# 上下文监测：要不要跑？（决策矩阵）

> 一句话：**宿主自己压缩上下文的时候，别跑监测脚本；不压缩的时候，必须跑。**
> 脚本本体在 [`../tools/`](../tools/)；本文回答「我该不该启动它」。

---

## 1. 决策矩阵（照这张表做）

| 你的宿主情况 | 要不要跑脚本 | 为什么 |
|---|---|---|
| **卸载了 compaction 插件** | ✅ **要跑** | 上下文不会自己压。会话一路涨到上限后，你会突然被截断/报错，且**没有任何预警**。脚本按阈值（官方 DS 65% / 其它 85%）提醒你「该换会话了」或「该手动 `/compact` 了」。 |
| **装了 compaction 但配了 `auto:false`** | ✅ **要跑** | 同上：插件在但自动压缩关着，等于不压缩。 |
| **装了自动压缩（`auto:true`）** | ⚠️ **越线告警不要跑；压缩检出可以要** | 「快到上限」的告警在自动压缩环境里是重复的（宿主压完脚本还在喊），冷却+迟滞也会被反复触发。但**压缩检出**（v0.1.6 新增，见 §8）恰好补上宿主不告诉你的那件事：会话刚被压过、摘要已替换原文 → 用 `--brief` 让 worker/judge 重新对一遍真源。要只留这一路，就 `--no-ingress` 加调大 `--drop-pts`。 |
| **不确定自己是哪种** | 🔍 **先跑面板「一键体检」** | 诊断项会读 profile patch 里的 `compaction-basic` 配置，直接告诉你 compaction 是开还是关。看完再决定。 |

> **两者冲突时会被诊断标出来**：如果你「装了自动压缩」还在跑脚本，诊断会把 `monitor` 这项标 `bad`，并给 fix「建议停止」。
> 这个检查就是为了防止你忘了关。

---

## 2. 为什么会有这个脚本（背景）

DSH 的上下文压缩是**插件**（`compaction-basic`）的事，不是内核自带的。所以存在两种合法状态：

- **有压缩**：会话涨到一定程度自动压，老消息被摘要，会话能一直跑下去；
- **没压缩**：会话涨到上限就真的到顶了，需要人介入（换新会话 / 手动 `/compact` / 结束任务）。

**没压缩的时候没人告诉你还剩多少**——这就是脚本存在的理由。它把「还剩多少」变成一条可见的告警。

反过来，**有压缩的时候脚本就是多余的**：宿主已经在做这件事，而且它做得比脚本更准（它知道压缩前后发生了什么）。

---

## 3. 脚本到底读什么、写什么、改什么

| 动作 | 具体 |
|---|---|
| **读**（只读） | `<USERPROFILE>/.dsh/storages/session_projcache/sessions/*.json`（DSH 自己写的会话快照） |
| **写** | 只有三类：`ctx-alerts.log`（告警日志）、`ingress.jsonl`（告警事件，可选）、`ctx-monitor.pid`（pid 文件） |
| **改** | **什么都不改**。不写会话的 AGENTS.md / 提示词 / 配置，不调 DSH 接口改会话，不动任何状态文件。 |

> 「只读、不注入」是硬约束：这个脚本**永远不会**影响你正在跑的会话内容。

---

## 4. 阈值怎么定

默认两档：

| provider | 阈值 | 说明 |
|---|---|---|
| `deepseek-account`（官方 DS） | **65%** | 官方渠道上下文窗口通常是 1M，65% ≈ 65 万 token，留足余量做一轮完整工作 |
| 其余（trae / raccoon / qoder 等中转渠道） | **85%** | 中转渠道上下文窗口不一，用更保守的统一阈值 |

可以按 provider 单独覆盖：

```json
{ "ctxMonitor": { "thresholds": [{ "provider": "trae", "pct": 80 }] } }
```

匹配顺序：`thresholds` 精确匹配 → 官方判断 → `thresholdOther`。
**命中哪一档会写进告警行**（`[provider:trae]` / `[official]` / `[other]`），方便你核对是不是用对了档位。

---

## 5. 默认必须关闭

`ctxMonitor.enabled` 默认 **`false`**。

理由：这是**可选能力**，不是内核必需。一个包不能默认就在用户机器上起后台进程——那是不礼貌的，也会让「装了但没配」的人莫名其妙看到多个 node 进程。

**只有你显式点「启动」或跑 `--daemon`，它才会跑。**

---

## 6. 和面板的关系

| 能力 | 在哪 |
|---|---|
| 看 compaction 是开还是关 | 面板「一键体检」的诊断项 |
| 看 monitor 在不在跑 | 同上（会显示 pid 活/死） |
| 看 compaction 与 monitor 是否矛盾 | 同上（装了自动压缩还在跑 → 标 `bad`） |
| 改阈值 / 间隔 | 面板设置页「上下文监测」区（**热生效**，下一轮即用） |
| 启停进程 | 面板设置页的「启动 / 停止」按钮（只允许启包内 `tools/ctx-monitor.mjs`） |

**没有一个「自动帮你决定要不要跑」的开关**——这需要人判断（读诊断结果 + 知道自己装没装压缩插件），脚本不替你做这个决定。

---

## 7. 典型误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 装了自动压缩还一直跑脚本 | 重复告警 + 压缩后误判 | 停掉脚本（诊断会标 `bad` 提醒你） |
| 卸了压缩插件但没人跑脚本 | 会话到顶了才突然发现 | 启动脚本，让它提前提醒 |
| 以为脚本会「帮你压缩」 | 白等 | 它只**提醒**，压缩要么靠插件、要么你手动 `/compact` |
| 装了自动压缩就用 `--brief` 代替停脚本 | 越线告警仍在重复，噪音没消失 | 关 `alertIngress` 或调大 `--drop-pts`，把脚本降级成「压缩检出专用」 |
| 把 `--root` 留空（默认 cwd） | 看不到别的目录的会话 | 用 `--root=<你的工作区根>` 或设环境变量 `DSH_CTX_ROOT` |

## 8. 压缩检出与「压缩后自检」简报（v0.1.6 新增）

压缩本身不归脚本管，但**压缩之后当事人容易照着摘要干活**，而摘要不可信。脚本因此多做一件事：
**发现会话刚被压缩，就提醒去核对真源**。

### 判定

同一会话前后两轮：`上一轮 pct − 本轮 pct ≥ 15`（且上一轮 ≥ 30%）→ 判为被压缩。阈值可调 `--drop-pts` / `--drop-min-prev`。
命中后 `ctx-alerts.log` 记一行 `level:"compaction"`，并写一条 key 前缀 `ctx-compact:` 的 `【压缩后自检】` 事件。

### 简报文本

```bash
node ctx-monitor.mjs --brief=judge    # 给 judge
node ctx-monitor.mjs --brief=worker   # 给 worker
node ctx-monitor.mjs --brief=owner    # 只打共同段
```

只打印，不扫描、不写文件、不调任何 DSH 接口。

### judge 版口径（2026-11-09 定）

**摘要不可信；已收口（`done`）工单的证据极强、可置信；核对证据工单即可。**

- 判据优先级：**工单证据（`sa_evidence` 的清单 + 判词）> 交接文档 > 压缩摘要**；
- 已 `done` 的单：清单非空、孤儿 `orphan=0`、判词 `pass` 在 → **不用重审**；
- 要引用或复判，就核对那张单的证据本身，不必回摘要转述、不必全量重跑；
- 力气只花在：清单缺件、缺判词、新交来的 `ready` 单。

> 这条是「压缩后别照着摘要返工」的落字，也是为什么 `_test-ctx-monitor.mjs` 的计数断言改为「压缩事件另计」：
> 回落会多写一行，越线告警口径不变。
